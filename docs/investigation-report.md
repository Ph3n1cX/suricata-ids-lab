# Investigation Report: ICMP Echo Request Detection

## Summary

On 13 October 2026, Suricata 8.0.5 running on Kali Linux was used to observe a controlled ping test from the sensor at `10.0.2.7` to the VirtualBox NAT gateway at `10.0.2.1`. The initial custom ICMP rule matched both echo requests and echo replies. The rule was tuned with `itype:8`, Suricata was restarted, and a second test produced four alerts for echo requests only.

**Outcome:** The revised ICMP rule was validated against four generated ping requests. This confirms rule matching in this test, not malicious activity or compromise.

## Scope and environment

- Sensor OS: Kali Linux
- Suricata: 8.0.5 RELEASE
- Capture interface: `eth0`
- Capture method: AF_PACKET
- Sensor address: `10.0.2.7`
- Destination: `10.0.2.1`
- HOME_NET: `10.0.2.0/24`
- Test traffic: four ICMP echo requests generated by `ping -c 4 10.0.2.1`

## Validation steps and evidence

### 1. Configuration test

Command:

```bash
sudo suricata -T -c /etc/suricata/suricata.yaml -v
```

Observed result:

- Configuration loaded successfully.
- Two rule files were processed.
- 389 rules were successfully loaded.
- 0 rules failed and 0 were skipped.

### 2. Service status

The service was restarted using:

```bash
sudo systemctl restart suricata
sudo systemctl status suricata --no-pager
```

Observed result: service reported `active (running)` with a new main PID.

### 3. Initial rule behavior

The original rule was:

```suricata
alert icmp any any -> $HOME_NET any (msg:"ICMP Ping Detected"; sid:1000001; rev:1;)
```

The first test generated two alert records at approximately `2026-10-13 08:40:09 -0400`:

- `10.0.2.7 -> 10.0.2.1`, ICMP type 8 (echo request)
- `10.0.2.1 -> 10.0.2.7`, ICMP type 0 (echo reply)

This showed that the initial signature was broader than its name implied.

### 4. Rule tuning

The rule was changed to:

```suricata
alert icmp any any -> $HOME_NET any (msg:"ICMP Echo Request Detected"; itype:8; sid:1000001; rev:2;)
```

The `itype:8` option limits the signature to ICMP echo requests. The configuration test passed again, reporting 389 rules loaded and no rule failures or skips. Suricata was then restarted.

### 5. Retest

Command:

```bash
ping -c 4 10.0.2.1
sudo tail -n 10 /var/log/suricata/fast.log
```

Ping output reported four packets transmitted, four received, and 0% packet loss.

Four new revision-2 alerts appeared in `fast.log`:

| Timestamp (as logged by VM) | Source | Destination | Signature |
|---|---|---|---|
| 2026-10-13 08:46:18.821846 -0400 | 10.0.2.7 | 10.0.2.1 | ICMP Echo Request Detected |
| 2026-10-13 08:46:19.847307 -0400 | 10.0.2.7 | 10.0.2.1 | ICMP Echo Request Detected |
| 2026-10-13 08:46:20.848549 -0400 | 10.0.2.7 | 10.0.2.1 | ICMP Echo Request Detected |
| 2026-10-13 08:46:21.863098 -0400 | 10.0.2.7 | 10.0.2.1 | ICMP Echo Request Detected |

The VM's logs use the `-0400` timezone offset. Timestamps above are reproduced as logged and have not been converted to the user's local timezone.

## Analyst interpretation

- The signature generated one alert for each observed echo request in this four-packet test.
- The revised rule did not alert on the echo replies in the retest output.
- The activity was a deliberate benign connectivity test by the lab operator.
- The alert proves that the rule matched the observed packet type. It does not indicate an attack, successful intrusion, or compromised host.
- Suricata was operating as an IDS. No evidence in this test shows that packets were blocked.

## Limitations and follow-up

- This was a single simple ICMP test, not a comprehensive detection evaluation.
- The SSH and FTP rules have not been retested in this session.
- The TCP SYN threshold rule is named as an Nmap scan detector, but a SYN burst alone cannot identify Nmap specifically or prove scanning intent.
- The ICMP threshold rule does not verify that requests target multiple distinct hosts; it should not be treated as conclusive ping-sweep detection.
- Future work: improve and separately test the threshold rules, collect screenshots from the actual terminal, and optionally compare the fast log with valid EVE JSON records.

## Conclusion

The test demonstrated a basic detection-engineering workflow: validate configuration, observe an overly broad signature, tune it, restart the sensor, generate controlled traffic, and verify the new alert output. The result is suitable as an introductory learning-lab portfolio artifact with the stated limitations.
